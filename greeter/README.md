# Первое сообщение клиенту

Клиент оставляет на сайте заявку и указывает Telegram. Через несколько секунд
ему приходит сообщение с рабочего аккаунта: приветствие и номер обращения.
Дальше переписку ведёт менеджер.

## Почему отдельный процесс, а не CRM

Бот Telegram **не может написать первым**. Площадка разрешает ему отвечать
только тем, кто сам начал диалог, — поэтому в заказах и есть `telegramChatId`:
он заполняется, когда клиент пишет боту сам. У заявки с сайта такого диалога
нет, есть только никнейм.

Написать первым может лишь живой аккаунт. Его сессия — это полный вход
в Telegram, и держать её внутри CRM нельзя: там она оказалась бы в образе,
который собирается в CI и лежит в реестре. Поэтому воркер отдельный, а CRM
умеет ровно две вещи — отдать очередь и записать итог.

## Как работает

1. CRM принимает заявку с сайта и ставит `clientGreetedAt = NULL`.
2. Воркер раз в 5 секунд спрашивает `GET /order-photo/greeting/pending`.
3. Отправляет сообщение и возвращает итог в `POST /order-photo/greeting/mark`.

Состояние живёт в CRM, а не в воркере. Перезапуск контейнера ничего не теряет
и никому не пишет дважды.

В очередь попадают только заявки **с сайта** (`externalRequestId` начинается
с `web-photo`), только с телеграмом и только свежие — не старше 12 часов.
Заказы с Авито сюда не идут: там переписка уже ведётся на площадке.

## Итоги попытки

| Итог | Что значит |
|---|---|
| `sent` | сообщение доставлено |
| `privacy` | аккаунт не принимает сообщения от незнакомых |
| `not_found` | такого никнейма нет — почти всегда опечатка клиента |
| `blocked` | нас заблокировали |
| `flood` | Telegram попросил подождать дольше, чем мы готовы |
| `error` | прочий отказ площадки |

Отметка ставится в любом случае, даже при отказе: заказ, которому нельзя
написать, должен уйти из очереди, а не собирать попытки бесконечно. Итог виден
в карточке заказа — менеджер знает, дошло сообщение или писать самому.

## Настройка

В `.env` рядом с `docker-compose.prod.yml`:

```
TG_API_ID=...
TG_API_HASH=...
```

Взять на <https://my.telegram.org> → API development tools. `CRM_LEAD_TOKEN`
там уже есть — воркер ходит в CRM тем же токеном, что и сайт: это тот же
доверенный контур, наши процессы на нашем сервере.

Вход в аккаунт — один раз, вручную:

```bash
docker compose -f docker-compose.prod.yml run --rm greeter python login.py
```

Спросит номер, код из Telegram и пароль двухфакторной аутентификации.
Дальше:

```bash
docker compose -f docker-compose.prod.yml up -d greeter
docker compose -f docker-compose.prod.yml logs -f greeter
```

## Текст сообщения

Лежит в `message.txt`. Подстановки:

| Метка | Во что превращается |
|---|---|
| `{greeting}` | «Здравствуйте, Пётр!» или «Здравствуйте!», если имени нет |
| `{name}` | имя из заявки, может быть пустым |
| `{number}` | номер обращения |

`{greeting}` — отдельная метка, а не просто `{name}`, именно потому, что имени
может не быть: «Здравствуйте, !» выглядит как поломка.

После правки текста контейнер нужно пересобрать: `docker compose build greeter`.

## О чём стоит помнить

**Никнейм клиент вводит руками.** Проверить, что аккаунт принадлежит именно
ему, невозможно — существует только проверка формы записи. Клиент ошибся
буквой, и сообщение уходит незнакомому человеку. Поэтому в тексте по
умолчанию нет ничего лишнего: имя и номер обращения — всё. Не стоит добавлять
туда сумму заказа, телефон или состав: цена такой ошибки вырастет.

Более осторожный вариант — первое сообщение вообще без данных
(«Вы оставляли заявку на сайте, ответьте “да”»), а имя и номер отправлять
после ответа. Тогда опечатка не раскрывает ничего.

**Темп.** Между сообщениями 25–40 секунд, это задаётся `GREETER_SEND_DELAY`.
Первые сообщения незнакомым аккаунтам — самый рискованный для Telegram
шаблон: за него выдают `PEER_FLOOD`. При заявках в единицах за день запас
огромный, но снижать паузу незачем — выигрыш нулевой, а этот аккаунт
основной канал продаж.

Получив `PEER_FLOOD`, воркер останавливается на шесть часов и не помечает
заказ: тот останется в очереди и уйдёт после паузы.

## Переменные окружения

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `GREETER_POLL_SECONDS` | 5 | как часто спрашивать очередь |
| `GREETER_SEND_DELAY` | 25 | пауза между сообщениями, с |
| `GREETER_SEND_JITTER` | 15 | случайная добавка к паузе, с |
| `GREETER_PEER_FLOOD_PAUSE` | 21600 | пауза после `PEER_FLOOD`, с |
| `GREETER_MAX_FLOOD_WAIT` | 600 | дольше этого `FLOOD_WAIT` не ждём |
| `GREETER_SESSION` | `/session/tg_greeter` | путь к файлу сессии в томе |
