## PURPOSE

Этапы 06–13 принимались по отдельности: каждый доказывал свой кусок. Этап 14 доказывает, что куски
сходятся в одну цепочку на живых данных — и честно называет места, где цепочка рвётся не из-за дефекта,
а по природе данных (человек не дал cookie, заказ заведён руками с Авито).

Цепочка из мастер-плана (§ 14):

```text
реклама → визит → ClientID → UTM/yclid → товар → конфигуратор → заявка → LEAD → NEW → PAID →
выручка → себестоимость → прибыль → аналитика → dashboard → сравнение периодов → вывод
```

## 1. Ключевое решение метода (требует подтверждения Reviewer)

Приёмку предлагается вести **ретроспективно, на уже существующих реальных заказах**, а не создавать
контрольную заявку.

```text
ЗА ретроспективу   production — боевая CRM: тестовый заказ попадёт в выручку, в зарплатные начисления,
                   в очередь к Метрике (PAID уйдёт как реальная конверсия и испортит обучение Директа),
                   в план дня исполнителей. Удалять его потом — правка боевых данных, которую этот
                   проект запрещает. Данных за сентябрь достаточно: заявки с сайта с атрибуцией идут
                   с 09.2026, переходы в очереди есть (delivered 16), оплаченные заказы есть.
ПРОТИВ             ретроспектива не проверяет один участок целиком в реальном времени — «заявка прямо
                   сейчас» (сайт → CRM). Его предлагается закрыть staging-заявкой на сайте без создания
                   заказа в CRM (проверка полезной нагрузки на стороне сайта) либо наблюдением за первой
                   же реальной заявкой в окне приёмки.
```

Если Reviewer решит иначе — контрольный заказ возможен только с явной командой, с заранее описанным
способом его исключения из отчётности и с отметкой в Метрику **не** отправлять.
