## 2. H2 — access-логи без рекламных идентификаторов (следующая работа по hardening)

Задача заведена как первая к исполнению: она не трогает данные и обратима правкой конфигурации.

```text
ГДЕ       обе конфигурации nginx, а не одна:
          1) сайт   — web-photo/nginx-domain.conf (контейнер photo-web / фронт сайта)
          2) панель — frontend/nginx-photo.conf (контейнер raspechatka-frontend-1)
ЧТО       убрать query-string из строки access-лога либо маскировать yclid:
          log_format site '$remote_addr - [$time_local] "$request_method $uri" $status $body_bytes_sent "$http_user_agent"';
          либо map $args → $args_safe с заменой yclid=<цифры>
ПОЧЕМУ    22.09.2026 подтверждено: yclid пишут ОБА access-лога. В логе панели за час — 4 строки
          вида «GET /?yclid=<19–20 цифр>» от робота Яндекс.Метрики. Это рекламный идентификатор,
          не секрет и не PII в строгом смысле, но спецификация этапа 13 относит его к скану.
РЕШЕНИЕ ПО IP  остаётся за владельцем: $remote_addr — стандартная строка nginx, убирать её не обязательно.
```

### Обязательная проверка BEFORE/AFTER

```text
BEFORE   для каждого из двух контейнеров зафиксировать:
           docker logs --since 1h <контейнер> | grep -cE 'yclid=[0-9]{15,}'        → ожидаем > 0 хотя бы на одном
           пример строки (обезличенный, значения не выводить: yclid → <19-20-ЦИФР>, IP → <IP>)
           общее число строк access-лога за окно — чтобы AFTER сравнивался на сопоставимом трафике
ACTION   правка log_format в обеих конфигурациях → сборка образов через CI → выкладка штатным
         auto-update (без --no-deps ничего не делать вручную), nginx перечитывается автоматически
AFTER    те же две команды на том же окне (не меньше часа реального трафика, включая робота Метрики):
           совпадений yclid → 0 в обоих контейнерах
           строки access-лога продолжают писаться (счётчик > 0) — иначе сломан сам лог
           коды ответов и объёмы в логе совпадают по смыслу с BEFORE
STOP     access-лог опустел или перестал писаться; сайт/панель отдают не 200 на / и /interer/holst;
         сборка не прошла CI
ROLLBACK вернуть прежний log_format тем же путём (CI → auto-update); откат конфигурации данных не касается
```

## 4. Факты эксплуатации, которые нужно учитывать в любой из этих работ

```text
1. Планировщик привязан к моменту старта контейнера (см. SCHEDULER_RELIABILITY.md § 5):
   после пересоздания два наблюдаемых автоцикла = boot-цикл + следующий часовой цикл,
   то есть окно наблюдения после выкладки — не меньше часа с небольшим.
2. Выкладку делает только auto-update по метке :production; ручной запуск и таймер
   защищены единым замком (flock /var/lock/auto-update.lock) — второй проход выходит с «Пропуск».
3. Сверка сборки ждёт готовности контейнера ограниченно (12 попыток × 5 с) и различает
   «ещё не поднялся» и «работает не та сборка» — при hardening-выкладках смотреть именно эти строки.
```
