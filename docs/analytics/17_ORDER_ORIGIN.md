# 17_ORDER_ORIGIN.md — происхождение заказа

## Статус

```text
IMPLEMENTED / READY_FOR_ROLLOUT — 24.09.2026, ветка feature/analytics-foundation.
Базовая точка production: 8eabc05b5636ed8fa648d1f84c73079dbb5ab47f (этап 16).
Миграция одна, additive: 20260924010000_order_origin_website_unknown.
```

## Зачем

Аналитика умела считать сайт и умела считать бизнес, но не умела ответить на вопрос
«сколько заказов принёс сайт, а сколько Avito» — потому что заявки сайта сохранялись
как `LOCAL`, и то же значение мог выбрать сотрудник вручную. Этап 17 даёт одно
определение происхождения заказа и проводит его через метрики, панель и отчёт для ИИ.

**Происхождение заказа ≠ источник рекламы.** Происхождение отвечает, откуда заказ
взялся (сайт создал заявку сам или человек завёл её в CRM). Источник рекламы отвечает,
откуда человек пришёл на сайт (Яндекс.Директ, поиск, переход, прямой заход, UTM,
yclid, ClientID). Это разные измерения, и смешивать их нельзя: «выручка Avito» ничего
не говорит о работе сайта, а конверсия сайта, посчитанная по всем заказам CRM,
завышена ровно на ручные заказы.

## Модель

```text
EnumSourceOrder: AVITO | OZON | WB | LOCAL | WEBSITE | UNKNOWN
  WEBSITE  — заявку создал сайт (ставит сервер, из тела запроса не переопределяется);
  AVITO    — ручной заказ: выбран сотрудником либо канал по умолчанию;
  OZON/WB  — ручной заказ соответствующего маркетплейса;
  LOCAL    — ручной «местный» заказ;
  UNKNOWN  — историческое происхождение не доказано.
```

Новое поле не заводилось: `sourceOrder` подошёл по смыслу. Миграция только добавляет
два значения перечисления — существующие значения и данные не трогаются.

Канон живёт в `crm-new/src/order-photo/order-origin.ts`: список значений, канал по
умолчанию (`MANUAL_DEFAULT_ORIGIN`), признак заявки сайта и правила исторической
классификации. Аналитика импортирует оттуда же — второго определения не существует.

## Новые заказы

```text
Сайт     → sourceOrder = WEBSITE всегда, даже без UTM/yclid/ClientID.
           Подменить источник телом запроса нельзя: поля нет в контракте заявки,
           а валидация заявки отбрасывает лишние поля.
Ручной   → выбранный источник; не выбран — AVITO (MANUAL_DEFAULT_ORIGIN).
           Произвольная строка → 400 (@IsEnum).
```

В CRM появилось компактное поле «Источник заказа» при создании и в правке заказа;
в карточке заказа источник виден строкой. В списке выбора — только ручные каналы;
значение, поставленное сервером (WEBSITE) или историей (UNKNOWN), из списка не
пропадает, иначе правка соседнего поля молча переписала бы происхождение.

## Историческая классификация

```bash
npm run origin:backfill                     # dry-run: план, база не меняется
npm run origin:backfill -- --apply          # запись + снимок прежних значений
npm run origin:backfill -- --apply --snapshot /tmp/origin.json
```

```text
Правила (order-origin.ts::classifyHistoricalOrigin):
  есть web-photo-идентификатор заявки                → WEBSITE (доказано);
  сохранён AVITO / OZON / WB                         → остаётся собой (выбран человеком);
  сохранён WEBSITE                                   → остаётся WEBSITE;
  LOCAL без признака сайта                           → UNKNOWN (двойной смысл до этапа 17);
  источника нет и признаков нет                      → UNKNOWN;
  признак сайта + сохранённый чужой канал            → КОНФЛИКТ: не трогаем, печатаем.
Отсутствие ClientID/UTM/yclid НЕ является доказательством ничего.
Повторный apply даёт 0 изменений (проверено тестом и на production).
```

## Аналитика

```text
Срез «Каналы заказов» (GET /analytics/dashboard/sales-channels) теперь отдаёт все
происхождения, включая UNKNOWN, и деньги канала:
  crmLeads / acceptedOrders / paidOrders / cancelledOrders — наборы периода CRM;
  realizedRevenue / cogs / grossProfit / marginPct / averageCheck — P&L канала.

P&L канала считает ReportsService.pnlByOrigin тем же buildPnl, что и весь остальной
финансовый контур: своей формулы прибыли не появилось. Расходы и зарплаты по каналам
НЕ делятся (реклама и оборудование не принадлежат ни Avito, ни сайту), поэтому по
каналам показывается ВАЛОВАЯ прибыль, а чистая прибыль владельца остаётся одна на
весь бизнес. Корзина «все заказы» считается так же — без расходов, — поэтому сумма
каналов сходится с ней до рубля.
```

Воронка сайта не изменилась и по построению не может содержать ручные заказы: она
считается по целям Яндекс.Метрики (`computeSiteFunnel`), а заказы попадают в цели
только через выгрузку по ClientID. Воронка CRM остаётся отдельным блоком и показывает
бизнес целиком с разрезом по происхождению.

Этапы 10–12 проверены на смешение населённостей: поведение и рост сайта считаются по
данным Метрики, CRM-метрики помечены ограничением «итоги CRM включают не только сайт»
(`CRM_INCLUDES_OFFLINE`), описание метрик прямо говорит «не эффект сайта». Новых
детекторов не заводилось.

## Отчёт для ИИ

В каждом отчёте (7d/30d/90d/свой период) появился раздел `# ORDER ORIGIN`:

```text
таблица  Канал | Заявки | Принято | Оплачено | Выручка | COGS | Прибыль | Маржа | Средний чек
         строкой «Все заказы» — сумма каналов;
полнота  totalOrders, orderOriginCoveragePct, websiteOrders, avitoOrders,
         unknownOriginOrders; при UNKNOWN > 0 печатается явное ОГРАНИЧЕНИЕ ДАННЫХ;
методика WEBSITE / AVITO / UNKNOWN, запрет делить все заказы CRM на визиты сайта,
         запрет считать рост Avito конверсией сайта, разделение происхождения и рекламы.
```

Там же печатается сверка «сумма каналов против итога периода» по принятым,
оплаченным, выручке, себестоимости и валовой прибыли. Разница допустима только
объяснённая: себестоимость бумаги округляется вверх до рубля в КАЖДОЙ корзине
(правило этапа 08), поэтому на 30-дневном окне сумма каналов может быть на 1 ₽
больше итога. Это округление, а не вторая формула — отчёт называет его прямо.

Те же правила продублированы в `METRIC DEFINITIONS` и в инструкции для ИИ-аналитика.
Раздел «Каналы продаж» внутри PRODUCTS заменён ссылкой на ORDER ORIGIN, чтобы одни и
те же числа не печатались дважды.

## Ограничения

```text
- Прибыль по каналам валовая: распределять зарплату и рекламу по каналам нечем,
  выдуманный коэффициент был бы хуже отсутствия числа.
- UNKNOWN не «дозаполняется» со временем сам: это историческая категория.
  Новые заказы в неё не попадают — у каждого есть либо серверное, либо выбранное
  происхождение.
- Разрез по происхождению не заменяет рекламную атрибуцию: деньги по источникам
  трафика по-прежнему не раскладываются, пока ClientID есть у меньшинства заказов.
```
