## 2. Порядок в тике (фактический, лог 17.09 09:34:56–09:35:05)

```text
1. MetrikaAnalyticsSyncService.sync        «Метрика: синхронизация … (scheduler:daily) — SUCCESS, наборов 12, запросов 23»
2. MetrikaPeriodSnapshotService             «снимки периодов обновлены — 8/8, запросов 16»
3. hook growth:evaluate                     «Рост: автооценка — изменений 0, запросов снимков окон 2, ошибок 0»
4. hook insights:run                        «Сигналы: запуск daily — обнаружено 8, новых 8, …, ошибок 0»
```

Порядок хуков = порядок регистрации = порядок модулей в `app.module.ts` (GrowthModule раньше InsightsModule):
карточка `change.evaluation` в том же тике видит новую версию оценки (проверено Stage 12 rollout § 35.7).
Хуки выполняются только при SUCCESS/PARTIAL синхронизации; при FAILED/LOCKED/NOT_CONFIGURED — не выполняются.

## 3. Доказательства (тесты и production)

| Утверждение | Evidence |
|---|---|
| Наложение исключено | `metrika-analytics-sync.service.spec` «lock: два одновременных запуска — выполняется один, второй LOCKED»; `scheduler.spec` «тик во время идущего тика — пропускается»; `analytics-insights.service.spec` «висящий RUNNING моложе 10 мин → LOCKED»; production: `LOCKED` 0, параллельных RUNNING 0 |
| Рестарт не оставляет ложный SUCCESS | статус SUCCESS пишется после коммита транзакции набора (`metrika-sync-store`); убитый процесс оставляет RUNNING, который закрывается как FAILED (60 мин) — `spec` «зависший RUNNING старше часа»; сигналы: RUNNING → FAILED (10 мин) — F4 |
| Зависание обнаруживается | **[13]** `/analytics/ops/status`: `METRIKA_SYNC_STUCK` (RUNNING > 60 мин, CRITICAL), `INSIGHTS_RUN_STUCK` (> 10 мин), `OUTBOX_STUCK` (processing > 10 мин) |
| Ошибка сигналов/роста не откатывает синхронизацию | `scheduler.spec` «хуки после тика: ошибка хука не мешает остальным»; хук вызывается после того, как синхронизация уже вернула SUCCESS |
| Порядок хуков зафиксирован | § 2; Stage 12 rollout § 35.7 (порядок строк лога) |
| Календарные окна согласованы с Europe/Moscow | `calendarDateIn(now)` — дата по Москве определяет «новый день»; `rollingWindow` — полные московские дни; `periodBoundsUtc` переводит границы в UTC для запросов; окна этапов 11–12 — `observationCutoffOf(now, lastDataDay)` = вчера по Москве; тесты `metrika-dates.spec`, `scheduler.spec` «по Москве уже новый день (21:00 UTC)» |

## 4. STUCK-recovery (раздел 8)

| Состояние | Порог | Действие | Кто | Аудит | Идемпотентно |
|---|---|---|---|---|---|
| `MetrikaSyncRun.RUNNING` | > 60 мин | автоматически → FAILED (`lastError` «зависший запуск») при следующем запуске синхронизации; данные периода не трогаются (замена не дошла до коммита) | код (этап 07) | строка журнала | да — следующий тик пересинхронизирует период |
| `AnalyticsInsightRun.RUNNING` | > 10 мин | **[13]** автоматически → FAILED с текстом при следующем запуске | код | строка журнала + лог warn | да — запуск пересчитывает карточки, dedupe по отпечатку |
| `MetrikaOrderOutbox.processing` | > 10 мин | автоматически → pending (`lockedAt` сброшен) | код (этап 06) | `updatedAt`, лог | да — повторная отправка того же перехода; Метрика принимает файл заказа заново (`merge_mode=SAVE`) |
| `MetrikaOrderOutbox.failed` | любой возраст | **вручную**: `metrika:orders:status` → причина; `requeue` (после устранения) или `skip` (осознанно) | оператор (ADMIN) | `lastError`, `attemptCount`, статус | requeue не создаёт дублей: строка одна |
| планировщик молчит (нет тиков) | нет SUCCESS > 2 ч при включённом флаге | `METRIKA_SYNC_STALE`; действие — проверить лог и флаги, при необходимости перезапустить backend (rollout-процедура, не автомат) | оператор | лог, диагностика | рестарт → boot-тик суточный, идемпотентный |

Запрещено автоматизировать: массовый requeue failed-строк (historical mass resend), удаление журналов, `migrate resolve`.

## 5. Известные ограничения (не дефекты)

- Интервал тиков привязан к минуте старта контейнера (после recreate 17.09 09:33 — `:33`); при каждом рестарте первый тик — суточный.
- Между двумя процессами (например, 30-секундное окно при recreate без `--no-deps`) синхронизацию защищает advisory lock, а хуки роста и сигналов — только последовательность в процессе и уникальные индексы; compose recreate останавливает старый контейнер до старта нового, поэтому окно не возникает.
- Снимки пресетов обновляются и после FAILED синхронизации — намеренно (они не зависят от наборов).
