## Что выяснил аудит

Цепочка «клик → визит → заявка → заказ → оплата» на сайте уже собрана:
`yclid`, UTM, первая страница визита и страница заявки запоминаются на визит
и уходят в CRM вместе с заявкой; продуктовые цели (`lead_submitted_photo`,
`lead_submitted_canvas`, `lead_submitted_tshirt`) вызываются только после
успешного ответа сервера. Ломать там было нечего.

Ломалось другое — измерение и его чтение:

```text
Покрытие ClientID 11 %      считалось ПО ВСЕМ принятым заказам, включая 343
                            ручных заказа Avito, у которых ClientID нет и быть
                            не может. По заказам САЙТА покрытие было 56 %.
63 пропуска no_client_id    из них 61 — те же ручные заказы. Настоящих пробелов
                            (заказ сайта без идентификатора) — единицы.
UTM 0 %                     меток нет в самих объявлениях: Директ передаёт
                            yclid автоматически, а UTM ставит рекламодатель.
ClientID у части заявок     счётчик грузится только после согласия на cookie,
                            а спрашивали идентификатор в момент отправки формы:
                            за 800 мс он не всегда успевал ответить.
Расходов нет вовсе          поэтому CPL, CPA, CPO, ROAS и ROMI не считались.
```

## Что сделано

### 1. Покрытие считается по заказам сайта

`DataQualityMetrics` получил четыре поля: `websiteAccepted`,
`websiteClientIdCoverage`, `websiteYclidCoverage`, `websiteUtmCoverage` и
`websiteWithoutIdentity` — заказы сайта, которые нельзя связать с визитом
вообще. Отчёт печатает их вместо общего числа: чинить можно только то, что
сайт создал сам.

### 2. ClientID спрашивается заранее

`primeYandexClientId()` вызывается при загрузке счётчика (несколько попыток
с нарастающей паузой) и запоминает идентификатор на визит. Отправка формы
получает готовое значение мгновенно, гонка исчезла. Счётчик заблокирован или
согласие не дано — заявка уходит без ClientID и без задержки.

### 3. Второй идентификатор: офлайн-конверсии по yclid

Заказ без ClientID, но с меткой клика Директа больше не обязан теряться:
очередь может отправить его офлайн-конверсией
(`POST /management/v1/counter/{id}/offline_conversions/upload?client_id_type=YCLID`).

Канал **выключен по умолчанию** и включается только целями в настройках.
Причина: цели «CRM: Заказ создан/оплачен» достигаются самой загрузкой
заказов CDP, и отправка офлайн-конверсии на ту же цель дала бы двойной счёт.
Канал требует ОТДЕЛЬНЫХ целей — их заводит владелец.

### 4. Честные причины пропусков

```text
manual_order_no_web_identity  ручной заказ — идентификатора визита не бывает (норма)
no_client_id                  заказ САЙТА без ClientID и без метки клика (пробел)
yclid_channel_disabled        метка клика есть, канал в кабинете не настроен
```

Отчёт печатает расшифровку рядом с числом: раньше таблица пропусков читалась
как список поломок, хотя состояла в основном из ожидаемого.

### 5. Рекламные расходы и окупаемость

Появилась таблица `AdSpend` (день, площадка, кампания, расход, клики, показы)
и импорт из выгрузки кабинета:

```bash
npm run ads:import -- --file /tmp/direct.csv           # разбор без записи
npm run ads:import -- --file /tmp/direct.csv --apply   # записать
```

Разбор терпим к формату: запятая, точка с запятой или табуляция; «1 234,56»
и «1234.56»; заголовки по-русски и по-английски; строки глубже дня
схлопываются по (день, кампания). Запись идемпотентна: повторная загрузка
того же отчёта переписывает строки, а не удваивает расход.

Контракт метрик `SpendMetrics` наполнился: spend, clicks, impressions, CPL,
CPA, CPO, ROAS, ROMI и признак `attributionReliable`. Три честных состояния:

```text
UNAVAILABLE_NO_SPEND_DATA     расходов за период нет — считать нечего
ATTRIBUTION_COVERAGE_TOO_LOW  расход известен, но связь «клик → заказ» доказана
                              меньше чем у половины заказов сайта: цена заявки
                              и заказа считается, ROAS и ROMI — нет
AVAILABLE                     считается всё
```

Два правила зашиты в расчёт: рекламе приписываются только заказы
происхождения WEBSITE, и деньги считаются канонической методикой P&L —
второй формулы прибыли не появилось.

## Внешние действия владельца

Их нельзя выполнить из репозитория.

### A. UTM-шаблон в Яндекс.Директе (5 минут, даёт UTM > 0 %)

В кабинете Директа → Кампания → «Ссылки» → параметры к ссылке объявления:

```text
utm_source=yandex&utm_medium=cpc&utm_campaign={campaign_id}&utm_content={ad_id}&utm_term={keyword}
```

Сайт уже умеет их принимать и хранить на визит; ничего дорабатывать не нужно.
`yclid` Директ подставляет сам — вручную его прописывать не надо.

### B. Выгрузка расходов (пока нет доступа к API Директа)

Кабинет → Статистика → «Мастер отчётов»: срез «День» + «Кампания», столбцы
«Показы», «Клики», «Расход (руб.)». Экспорт CSV → на сервере:

```bash
docker cp отчёт.csv raspechatka-backend-1:/tmp/direct.csv
docker exec raspechatka-backend-1 npm run ads:import -- --file /tmp/direct.csv
docker exec raspechatka-backend-1 npm run ads:import -- --file /tmp/direct.csv --apply
```

После этого отчёт и дашборд считают CPL/CPA/CPO, а при достаточном покрытии
атрибуции — ROAS и ROMI.

Автоматический импорт из API Директа не делался: для него нужен OAuth-токен
приложения с доступом к кабинету. Появится токен — адаптер положит те же
строки в ту же таблицу, менять расчёт не придётся.

### C. Канал офлайн-конверсий по yclid (по желанию)

1. В Метрике завести ОТДЕЛЬНЫЕ цели типа «JavaScript-событие», например
   `crm_created_ad` и `crm_paid_ad`. Отдельные — чтобы не удваивать
   конверсии, которые уже приходят загрузкой заказов CDP.
2. Прописать их идентификаторы в окружение бэкенда:

```text
YANDEX_METRIKA_YCLID_TARGET_CREATED=crm_created_ad
YANDEX_METRIKA_YCLID_TARGET_PAID=crm_paid_ad
YANDEX_METRIKA_YCLID_TARGET_CANCELLED=
```

3. Проверить на одном заказе:
   `npm run metrika:orders -- preview <orderId>` — покажет файл конверсии,
   ничего не отправляя.

Пока переменных нет, канал молчит: ни одного запроса наружу.

## Что проверить через 7 дней

```text
- покрытие ClientID у новых заказов САЙТА (должно вырасти: идентификатор
  спрашивается заранее);
- число пропусков no_client_id — только заказы сайта, ручные туда больше
  не попадают;
- UTM > 0 %, если шаблон в Директе поставлен;
- расходы в системе и CPL/CPA — после первого импорта;
- ROAS и ROMI появятся, когда покрытие атрибуции перевалит за половину.
```

## Ограничения

```text
- Счётчик Метрики загружается только после согласия на cookie (152-ФЗ).
  Пока человек не согласился, ClientID не существует — это не ошибка кода,
  и 100 % покрытия на всём трафике не будет.
- yclid от согласия не зависит: для рекламного трафика он и есть страховка.
- Автоимпорт расходов из API Директа не реализован — нужен OAuth-доступ.
- Канал офлайн-конверсий по yclid не проверялся на живом кабинете: он
  выключен до тех пор, пока владелец не заведёт цели и не подтвердит
  первый файл через preview.
```
