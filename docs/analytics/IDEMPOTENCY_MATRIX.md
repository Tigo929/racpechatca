## Инвариант «SUCCESS = committed usable state» — где проверен

- Синхронизация: статус набора выставляется после успешного `$transaction` замены (store); падение транзакции → FAILED и прежние строки целы (sync.spec «падение транзакции записи»).
- Сигналы: карточки, версии и итоговая строка журнала пишутся в одной транзакции; исключение → `FAILED` через `finishRun`, карточек запуска нет (service.spec «ошибка контекста → FAILED в журнале»).
- Рост: версия оценки — одна вставка; неудача → исключение хука, лог warn, версии нет.
- Outbox: строка переводится в `delivered` только после ответа API с `uploading_id`.

## Где идемпотентность обеспечивается детерминизмом, а не ключами

- Каноническая нагрузка карточки этапа 12: сортированные ключи, числа с округлением 1e-6, без `freshness`/`generatedAt`/`period`/`baselinePeriod`/ссылок на `sync_run`.
- **[13]** Порядок пересекающихся изменений (`overlappingChanges`) — `startedAt, id`: без него текст confounder `OVERLAPPING_CHANGE` и `relatedChangeIds` менялись местами после restore (обнаружено drill 17.09), что дало бы новую версию шести карточек без новых данных.
