## Два бизнес-правила, которые теперь закреплены кодом и тестами

```text
1. SALARY PAYOUT IS NOT CUSTOMER PAYMENT DATE.
   Выплата зарплаты исполнителю (SalaryService.createPaymentByAccruals) закрывает расчёт
   с сотрудником, а не фиксирует поступление денег от клиента. Одна выплата 16.09.2026
   перевела 40 заказов в «Оплачен» за две секунды при медиане отставания от отгрузки
   в неделю. Поэтому на этом пути дата оплаты не ставится ни в каком виде.

2. HISTORICAL NULL clientPaidAt VALUES ARE NOT BACKFILLED OR INFERRED.
   56 существующих пустых значений остаются пустыми. Дата не выводится ни из StatusHistory,
   ни из даты выплаты, ни из SENT, ни из даты создания заказа. Неизвестно — значит неизвестно.
```

## Что изменилось

### Backend

| Путь в «Оплачен» | Было | Стало |
|---|---|---|
| Ручной перевод (`PATCH /order-photo/:id/status`) | дата = момент нажатия | дата = **переданная фактическая**, если её указали; иначе прежний момент нажатия |
| Выплата зарплаты (`SalaryService`) | даты нет | даты по-прежнему нет; выплата **возвращает список** заказов, оставшихся без даты |
| Создание заказа сразу оплаченным | даты нет | принимает фактическую дату **только** с оплаченным статусом (сейчас недостижимо: создание ограничено LEAD/NEW) |
| Заказ уже PAID, даты нет | указать негде | новое узкое действие `PATCH /order-photo/:id/paid-at`, ADMIN, только пока поле пусто |

```text
Неизменяемость: заполненная дата не перезаписывается никогда — ни повторным PAID, ни
передачей другой даты (400 «Дата оплаты уже зафиксирована и не меняется»), ни обычным
редактированием заказа (в его DTO поля нет — закреплено тестом).
```

### Валидация даты и часовой пояс

```text
принимается    «2026-09-16» (московский календарный день) или полный момент ISO
день → момент  начало московских суток: 2026-09-16 → 2026-09-15T21:00:00Z
               (используется существующий контракт периодов: MOSCOW_OFFSET_MINUTES
               из analytics-period.ts и calendarDateIn из metrika-dates.ts — своего
               «полудня MSK» не вводили)
границы        не в будущем; не раньше createdAt заказа; мусор → 400 с понятным текстом
проверено      день пользователя остаётся тем же днём в отчётах, в том числе на стыке
               месяца: 31.08 остаётся августом, 01.09 — сентябрём
```

### Frontend

```text
карточка заказа   оплачен и дата есть      → «Оплата получена: 16 сент. 2026»
                  оплачен и даты нет       → «Дата оплаты не указана»
                                             + кнопка «Указать дату оплаты» (только ADMIN)
                  не оплачен               → блок не показывается
перевод в PAID    администратор жмёт «Оплачен» → панель «Когда получены деньги?»:
                  выбрал дату  → «Оплачен этой датой»
                  оставил пусто → «Оплачен сегодня» (прежнее поведение)
правка            уже зафиксированную дату интерфейс изменить не даёт
```

## Аналитика не менялась

```text
recognitionDate = clientPaidAt ?? completedAt ?? statusChangedAt ?? sentAt ?? createdAt — как было.
Ни один файл src/analytics/** и src/reports/** не изменён.
Появление достоверной даты лишь переносит конкретный заказ на его собственный день:
заказ 20260909-091 без даты признаётся 16.09 (statusChangedAt), с датой 14.09 — четырнадцатым.
Это и есть цель D1 — и владелец должен знать: для новых заказов выручка будет попадать
в месяц оплаты, а не отгрузки. Задним числом ничего не переносится.
```
