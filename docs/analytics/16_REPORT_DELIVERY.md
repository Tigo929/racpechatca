## Что сделано

Отчёт этапа 15 теперь заказывается кнопкой в панели: **Аналитика → Отчёты для ИИ →
выбрать период → «Сформировать отчёт» → скачать MD**. Ни SSH, ни команд, ни доступа
к серверу владельцу больше не нужно.

## Главный инвариант

```text
Stage 16 не создаёт аналитики. API и интерфейс — только доставка.
Кнопка и командная строка зовут одну функцию generateReport (report/report-generate.ts),
которая собирает цепочку collect → build → markdown → html. Ни выручка, ни прибыль,
ни воронка, ни атрибуция, ни прогноз здесь заново не считаются — это закреплено тестом,
который читает исходники воркера, CLI и сервиса и падает при любой попытке считать
самостоятельно.
```

## База данных

Одна новая таблица `AnalyticsReport` (миграция `20260923010000_analytics_report_delivery`):
только метаданные — статус, тип периода, границы, кто и когда заказал, когда готов, сборка,
имена и размеры файлов, безопасный текст ошибки. **Содержимое отчёта в базе не хранится.**
Существующие таблицы заказов и аналитики миграция не трогает, данные не переносятся.

Статусы: `QUEUED → GENERATING → READY` либо `FAILED`.

## API

```text
POST   /analytics/report                     заказать (preset 7d|30d либо dateFrom/dateTo)
GET    /analytics/report?limit=&offset=      список метаданных, без содержимого
GET    /analytics/report/:id                 статус, период, размеры, сборка, ошибка
GET    /analytics/report/:id/download?format=md|html   файл вложением

Все маршруты: JwtAuthGuard + RolesGuard + @Roles(ADMIN). Без токена 401, другая роль 403.
POST не ждёт генерацию: возвращает { id, status: 'QUEUED' } сразу.
Период: текущий неполный московский день не входит; конец не в будущем; свой период ≤ 366 дней.
Повторный заказ того же периода, пока прежний не готов, возвращает тот же заказ.
```

## Воркер

```text
Опрос очереди раз в 10 секунд в том же процессе — без Redis и брокеров: ставить
инфраструктуру ради нескольких отчётов в неделю на сервер с одним ядром незачем.
Параллельности нет: флаг в процессе плюс захват строки (updateMany QUEUED → GENERATING
отдаёт ровно одному вызову).

Порядок: взять QUEUED → GENERATING → собрать отчёт генератором этапа 15 → скан на ПДн и
секреты → атомарно записать MD и HTML (через .tmp и переименование) → READY.
Любая ошибка: удалить недописанные файлы, поставить FAILED с текстом «Не удалось
сформировать отчёт». Частично готовый отчёт READY не становится никогда.
После каждого готового отчёта запускается уборка.
```

## Хранение файлов

```text
Каталог:   /app/data/analytics-reports/<id>/analytics-report-<от>_<до>.{md,html}
На хосте:  /opt/raspechatka/data/analytics-reports  (bind-mount в compose, переменная
           ANALYTICS_REPORTS_DIR)
Не в образе, не в контейнерной ФС, не в git (.gitignore), не в публичном каталоге nginx.
Наружу каталог не отдаётся: файл доступен только через авторизованный маршрут скачивания.
```

## Присмотр за очередью (FIX_01)

```text
ПРОБЛЕМА   backend может перезапуститься между QUEUED → GENERATING и READY:
           строка остаётся в GENERATING, файлов нет, отчёт «формируется» вечно,
           и владельцу нужен администратор. Так быть не должно.

ВОЗВРАТ    заказ в GENERATING дольше 15 минут считается брошенным:
           удаляются его недописанные файлы (только его каталог),
           статус возвращается в QUEUED, служебные поля и текст ошибки очищаются,
           период и заказчик не меняются, второй отчёт не создаётся.
           Воркер собирает отчёт заново обычным проходом.
КОГДА      при старте воркера (обычный перезапуск чинит очередь сам) и далее
           в суточном цикле присмотра.
ПОЧЕМУ 15 мин  реальная генерация занимает секунды; 15 минут — заведомо больше
           любой нормальной задержки и заметно меньше человеческого терпения.
БЕЗ МИГРАЦИИ   признак «давно в работе» берётся из существующего updatedAt:
           он обновляется в момент захвата строки воркером. Новой колонки
           (generationStartedAt) не понадобилось.
```

## Уборка

```text
Своя, отдельная от retention аналитики (этап 13): тот механизм и его --apply здесь
не используются вообще.

КОГДА   при старте воркера и далее раз в 24 часа — уборка не зависит от того,
        заказывал ли кто-то новый отчёт (FIX_01). Дополнительно отрабатывает
        после каждого успешно собранного отчёта.
ПРАВИЛО удаляем завершённые отчёты старше 180 дней и всё, что вышло за
        50 последних готовых — применяется более строгое ограничение.
ПОРЯДОК сначала файлы (MD и HTML), затем запись метаданных.
УСТОЙЧИВОСТЬ  отчёты обрабатываются по одному: пропавший файл или сбой на одной
        записи не прекращает уборку остальных, в журнал уходит предупреждение.
        Наружу через API пути файловой системы не выводятся.
НИКОГДА заказы в QUEUED и GENERATING обычная уборка не трогает; брошенный
        GENERATING сначала проходит через возврат в очередь (см. выше).
```

## Интерфейс

```text
Вкладка «Отчёты для ИИ» в разделе аналитики (только ADMIN видит раздел аналитики).
Форма: период (7 полных дней / 30 полных дней / свой), для своего — две даты.
Кнопка «Сформировать отчёт»; пока что-то в очереди — «Формируется…» и кнопка заблокирована.
Список: период, когда заказан, статус (В очереди / Формируется / Готов / Ошибка),
размер, сборка, действия.
Действия готового: «Скачать MD для ИИ» (основное) и «Печатная версия».
Подсказки: текущий день в период не входит; PDF — печать браузера «Сохранить как PDF».
Уже сформированный отчёт не редактируется и не перезаписывается.
```

## Безопасность

```text
Доступ          только ADMIN на всех четырёх маршрутах (гарды + @Roles).
Путь            пользователь передаёт только id (uuid) и формат (md|html). Имя файла
                берётся из метаданных; идентификатор проверяется регуляркой uuid;
                каталог обязан остаться внутри хранилища; имя файла — без разделителей
                пути. Обход каталога закрыт тестами.
Содержимое      перед READY файл проходит скан по 11 шаблонам: почта, телефон, IP,
                длинные идентификаторы (ClientID/yclid), yclid в ссылке, cookie,
                заголовок авторизации, JWT, OAuth-токен, строка подключения к БД,
                секреты в переменных. Нашлось — FAILED, файл пользователю не отдаётся.
                В сообщение попадают имена шаблонов, но не значения.
Ошибки          наружу уходит «Не удалось сформировать отчёт»; SQL, пути и исключения
                остаются в логах сервера.
HTML            статичный, без внешних скриптов и CDN; отдаётся вложением с
                Content-Security-Policy: default-src 'none' и X-Content-Type-Options: nosniff.
```
