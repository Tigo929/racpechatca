# 03_HISTORICAL_BACKFILL.md

# Этап 03 — Исторический backfill аналитических данных

## Статус

```text
REVIEW
```

> Исполнитель не имеет права самостоятельно ставить этапу `DONE`.
> После выполнения этап переводится в `REVIEW`.
> Решение `DONE / NEEDS_FIX / BLOCKED` принимает ChatGPT после проверки отчёта.

---

# 1. Входной контекст

Этап `02_ANALYTICS_DATA_MODEL` принят.

Подтверждено:

- в `OrderPhoto` существуют структурированные поля аналитической атрибуции;
- поле страницы конверсии называется:

```text
conversionPageUrl
```

и означает:

> URL страницы, на которой пользователь отправил заявку.

- настоящий first-touch landing URL пока НЕ сохраняется;
- `clientPaidAt` фиксирует первый переход в `PAID`;
- новые заявки сохраняют structured attribution;
- UTM теперь доходят для всех релевантных форм;
- `master` пока не содержит изменений этапа 02;
- рабочая ветка:

```text
feature/analytics-foundation
```

---

# 2. Цель этапа

Восстановить максимально возможную историческую аналитику из уже существующих данных CRM.

Нужно перенести исторические значения из свободного текста и истории статусов в новые структурированные поля.

Главный принцип:

> Backfill должен восстанавливать только то, что можно подтвердить по существующим данным. Нельзя придумывать отсутствующую историю.

---

# 3. Источники исторических данных

## 3.1. OrderPhoto.note

По аудиту там исторически встречаются:

```text
Yandex ClientID: ...
yclid: ...
Страница: ...
```

Из этого источника можно потенциально восстановить:

```text
yandexClientId
yclid
conversionPageUrl
```

Важно:

`Страница:` — это страница отправки заявки, а не first-touch landing page.

Записывать её только в:

```text
conversionPageUrl
```

---

## 3.2. ItemTshirt.designNote

Исторически там могли сохраняться UTM футболок.

Потенциально:

```text
utmSource
utmMedium
utmCampaign
```

Если реально присутствуют:

```text
utmContent
utmTerm
```

можно восстановить и их.

Но нельзя предполагать наличие полей — сначала проверить фактический формат данных.

---

## 3.3. StatusHistory

Использовать для восстановления:

```text
clientPaidAt
```

Правило:

> `clientPaidAt` = timestamp самого первого подтверждённого перехода заказа в `PAID`.

Не использовать последний переход.

Не использовать текущий `statusChangedAt` как замену истории, если нет доказательства, что это именно дата оплаты.

---

# 4. Известные временные ограничения

По аудиту:

```text
StatusHistory существует с 13.06.2026
```

Следовательно:

> до 13.06.2026 надёжно восстановить `clientPaidAt` из истории невозможно.

---

Исторический:

```text
yclid
```

начал попадать в заявки ориентировочно с:

```text
09.06.2026
```

---

Исторический:

```text
yandexClientId
```

начал попадать ориентировочно с:

```text
13.08.2026
```

---

Эти даты являются ограничениями данных, а НЕ поводом синтетически заполнять более ранние строки.

---

# 5. Важное ограничение по UTM

На этапе 02 обнаружено:

> До исправления UTM реально отправлялись не всеми формами.

Фото и холст исторически не передавали UTM тем же способом, что футболки.

Поэтому:

- не генерировать UTM для старых фото/холстов;
- не выводить UTM из URL, если это отдельно не подтверждено историческими данными;
- не переносить UTM между заказами одного клиента;
- не считать отсутствие UTM ошибкой backfill.

Backfill восстанавливает только фактически сохранённые данные.

---

# 6. Основные правила безопасности

## 6.1. Не перезаписывать существующие structured values

Если поле уже заполнено:

```text
yandexClientId != null
```

backfill не должен его менять.

То же правило для:

```text
yclid
utmSource
utmMedium
utmCampaign
utmContent
utmTerm
conversionPageUrl
clientPaidAt
```

Приоритет:

```text
существующее структурированное значение
>
исторически распарсенное значение
```

---

## 6.2. Идемпотентность

Повторный запуск должен приводить к тому же результату.

```text
run #1 → N обновлений
run #2 → 0 дополнительных корректных обновлений
```

Повторный запуск не должен:

- менять уже заполненные значения;
- дублировать записи;
- менять даты;
- повреждать note/designNote;
- создавать новые сущности.

---

## 6.3. Исходный текст не удалять

Не изменять и не очищать:

```text
OrderPhoto.note
ItemTshirt.designNote
StatusHistory
```

Они остаются историческим источником.

# 7. Формат реализации

Предпочтительно реализовать отдельный управляемый backfill script/command внутри CRM.

Например:

```text

```

или аналогичная команда согласно архитектуре проекта.

Требования:

```text
--dry-run
```

должен быть режимом по умолчанию или явно поддерживаться.

Применение изменений должно требовать осознанного действия:

```text
--apply
```

или эквивалент.

Нельзя при обычном старте приложения автоматически запускать исторический backfill.

# 8. Dry-run

Dry-run не меняет БД.

Он должен показать минимум:

```text
сколько OrderPhoto просмотрено

сколько найдено:
- yandexClientId
- yclid
- conversionPageUrl
- utmSource
- utmMedium
- utmCampaign
- utmContent
- utmTerm
- clientPaidAt

сколько значений:
- будет заполнено
- пропущено, потому что уже заполнено
- не удалось распарсить
- имеет конфликт
```

---

# 9. Конфликты

Если историческое значение конфликтует с уже существующим structured value:

пример:

```text
OrderPhoto.yandexClientId = AAA
note содержит Yandex ClientID: BBB
```

не перезаписывать.

Записать конфликт в отчёт.

Нужно иметь счётчик:

```text
conflicts
```

и желательно безопасный идентификатор заказа для расследования.

Не выводить чувствительные данные целиком в production logs без необходимости.

---

# 10. Парсинг note

Парсер должен быть:

- устойчив к пробелам;
- устойчив к отсутствующим строкам;
- не падать на произвольном пользовательском тексте;
- не использовать слишком широкий regex, который может захватить соседний текст.

Нужно сначала исследовать реальные варианты `note`.

В отчёте показать обнаруженные форматы.

Пример целевых маркеров:

```text
Yandex ClientID:
yclid:
Страница:
```

Но не считать этот пример единственно возможным без проверки данных.

---

# 11. Парсинг UTM

Перед реализацией:

1. исследовать реальные `ItemTshirt.designNote`;
2. определить точный формат;
3. собрать parser под реальные данные;
4. покрыть варианты тестами.

Если `utmContent` / `utmTerm` исторически не сохранялись:

```text
оставить null
```

Не выводить их косвенно из других значений.

# 12. Восстановление clientPaidAt

Для каждого заказа, где:

```text
clientPaidAt == null
```

найти первый `StatusHistory`, соответствующий переходу:

```text
* → PAID
```

и использовать его timestamp.

Если перехода нет:

```text
clientPaidAt остаётся null
```

Даже если текущий статус заказа:

```text
PAID
COMPLETED
DONE
SENT
```

не делать догадку без подтверждённой истории.

# 13. Граница признания оплаты

На этом этапе НЕ решается бизнес-вопрос:

Backfill использует только формальное событие:


# 15. Production safety

На этом этапе:

> НЕ запускать `--apply` на production без отдельной команды владельца.

Разрешается:

- dry-run на production, если он гарантированно read-only и безопасен;
- полноценный `--apply` на локальной/временной копии production DB;
- тесты на копии.

Если исполнитель считает, что production dry-run тоже нежелателен — объяснить и использовать копию.

# 21. Decision Gate для ChatGPT

## DONE

Этап принимается, если:

- backfill не перезаписывает structured data;
- parser основан на реальных форматах;
- `conversionPageUrl` не называется landing page;
- `clientPaidAt` берётся из первого подтверждённого PAID;
- неподтверждённые старые оплаты не выдумываются;
- script идемпотентен;
- dry-run существует;
- production apply не запускался без разрешения;
- apply проверен на копии;
- второй apply/dry-run подтверждает идемпотентность;
- тесты проходят;
- конфликты обработаны безопасно.

Тогда:

```text
03_HISTORICAL_BACKFILL = DONE
```

Следующий файл:

```text
04_EVENT_MODEL.md
```

---

## NEEDS_FIX

Если проблема исправима внутри этапа:

```text
03_HISTORICAL_BACKFILL = IN_PROGRESS
```

Создать:

```text
03_HISTORICAL_BACKFILL_FIX_01.md
```

---

## BLOCKED

Если требуется решение владельца:

```text

```

## 5. PARSING RULES

**note.** Маркер — в начале строки (допускаются ведущие пробелы/табы),
после двоеточия — остаток строки, обрезанный по краям. Три маркера:
`Yandex ClientID:`, `yclid:`, `Страница:`. Значение проходит проверку:
ClientID — `^\d{5,32}$`; yclid — `^[A-Za-z0-9_-]{5,240}$`; страница —
`^https?://\S+$`. Маркер есть, значение не прошло — считается ошибкой
разбора (`parseFailures`), поле не заполняется. Маркер в середине фразы
(«…что такое Yandex ClientID: объяснил») не считается значением.
Несколько одинаковых маркеров — берётся первый. CRLF нормализуется.
Значение из `note` в `conversionPageUrl` — как страница заявки, не входа.

**designNote (UTM).** Строка `Источник: …` до точки-с-пробелом или конца;
делится по ` / `. Три части → source/medium/campaign. Одна → только
source. Две — только source, остаток помечен как неоднозначный и не
записывается: `filter(Boolean)` в старом коде выбрасывал пустые метки,
и по двум значениям не понять, чего нет — medium или campaign; угадывать
запрещено. `utmContent`/`utmTerm` не восстанавливаются — их не писали.
В боевой базе парсер не нашёл ни одной строки; оставлен, потому что

## 13. DEVIATIONS FROM SPEC

1. Команда запускается из `dist` (`node dist/…/run.js`), а не через
   ts-node: сгенерированный клиент Prisma импортируется с расширением
   `.js`, которое ts-node в этом проекте не разрешает; `dist` — это
   и есть боевой способ запуска. Локально требуется `npm run build`.
2. Парсер UTM реализован по формату из кода, а не по данным: данных нет
   вовсе (п. 11 требовал «собрать под реальные данные»). Покрыт тестами,
   в отчёте зафиксировано, что в боевой базе он ничего не находит.
