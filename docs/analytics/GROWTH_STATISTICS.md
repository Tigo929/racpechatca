## 2. Методы по виду метрики

### Доли (siteLeadRate, formStartRate, formErrorRate, matchedAcceptedRate, leadToAcceptedRate, leadToPaidRate)

- Интервал доли — Уилсона; интервал разности p₂ − p₁ — Ньюкомб, метод 10 (на границах Уилсона):
  `low = d − √((p₂ − l₂)² + (u₁ − p₁)²)`, `high = d + √((u₂ − p₂)² + (p₁ − l₁)²)`.
- Тест: z-тест двух долей с объединённой долей, если все ожидаемые частоты 2×2 ≥ 5; иначе точный тест Фишера
  (двусторонний p = сумма вероятностей таблиц не более вероятных, чем наблюдаемая).
- MDE (абсолютная разница): `(z_α + z_β) · √(p₁(1 − p₁)(1/n₁ + 1/n₂))`; относительная = MDE / p₁.
- Требуемая выборка на окно для эффекта r (Флейсс без поправки на непрерывность):
  `n = ((z_α √(2 p̄ q̄) + z_β √(p₁q₁ + p₂q₂)) / (p₂ − p₁))²`, p₂ = p₁(1 + r).
- Контроль: 5/100 → (0,02154; 0,11175); 56/70 → 48/80: (−0,3339; −0,0524) — пример Newcombe 1998 с обратным знаком;
  z 5/100 vs 15/100 = 2,357, p = 0,0184; Фишер 3/4 vs 1/4 = 0,4857; требуемая выборка 10 % → 15 % = 686 на группу.

### Счётчики за равные окна (visits, siteLeads, formStarts, leadAttempts, formErrors, matched*, crmLeads, acceptedOrders, paidOrders)

- Модель — пуассоновские интенсивности; при условии X₁ + X₂ = N, X₁ ~ Binomial(N, t₁/(t₁ + t₂)); двусторонний точный
  p-value; отношение интенсивностей after/before с интервалом через Уилсона для доли x₂/N; в API — как интервал
  относительного изменения (%).
- MDE относительное при базе λ = x₁/t₁: `(z_α + z_β) · √(λ/t₁ + λ/t₂) / λ`; требуемых событий в базовом окне для
  эффекта r: `(z_α + z_β)² (2 + r) / r²` (r = 0,2 → 432).
- Контроль: 10 → 20 за 7 и 7 дней: RR 2, p = 0,0987, интервал RR (0,952; 4,200).

### Средние по заказам (paidAov)

- Перцентильный бутстрэп разности средних по заказам когорт (детерминированное зерно); p-value не вычисляется;
  сигнал — интервал без нуля. Меньше 5 оплаченных в любом окне → `descriptive_only` и `STATISTICAL_TEST_UNAVAILABLE`.

### Суммы денег (contractValue, paidOrderValue, realizedRevenue, netProfit)

- Только описательно (`descriptive_only`, флаг `STATISTICAL_TEST_UNAVAILABLE`), вердикт не выше INSUFFICIENT_DATA:
  значимость сумм из агрегатов не изобретается.

## 3. Правила вердикта (`growth-compute.ts`)

```text
INCOMPARABLE       — METRIC_SCOPE_MISMATCH (первичная метрика не из области изменения) или окна несопоставимы
                     (PARTIAL_MEASUREMENT_PERIOD / METRIC_UNAVAILABLE_* / MEASUREMENT_DEFINITION_CHANGED)
INSUFFICIENT_DATA  — MATCHED_COVERAGE_LOW или COGS_INCOMPLETE; ZERO_DENOMINATOR; LOW_SAMPLE (знаменатель < 30 визитов
                     или < 5 заказов, событий < 5, бутстрэп < 5); SHORT_WINDOW (окно < 7 полных дней); descriptive_only;
                     статистика не значима и MDE (относительное) > 20 %
IMMATURE           — созревание метрики не MATURE (PARTIALLY_MATURE тоже не окончательно)
NO_CLEAR_CHANGE    — интервал включает 0 (и p ≥ α), при этом MDE ≤ 20 %: объёма хватало бы заметить целевой эффект
POSITIVE_SIGNAL /  — интервал не включает 0 и p < α (где есть); знак относительно ожидаемого направления
NEGATIVE_SIGNAL      (INCREASE / DECREASE) либо полярности метрики (higher-good / lower-good) при NEUTRAL
```

Сигнал — не доказательство: `causality = NOT_ESTABLISHED`, дисклеймер в каждой оценке, оговорки перечислены в
INTERPRETATION. Проценты прироста при INCOMPARABLE / IMMATURE / INSUFFICIENT_DATA показываются приглушённо с
подписью «не является выводом».

## 4. Созревание (`growth-maturity.ts`)

- Задержки заявка → принят, принят → оплата, заявка → оплата в календарных днях по Москве из жизненного цикла заказов
  (без PII); распределение: n, медиана, p75, p90; `sufficient` при n ≥ 20.
- Политика: класс `accepted` — p90 (заявка → принят), класс `paid` — p90 (заявка → оплата), потолок 45 дней; при
  недостатке истории — 7 / 14 дней и флаг `MATURITY_HISTORY_INSUFFICIENT`; `maturityDays` изменения переопределяет paid
  и ограничивает accepted сверху.
- Статус: `MATURE`, если `observationCutoff ≥ after.to + days`; `PARTIALLY_MATURE`, если прошла медиана; иначе `IMMATURE`.
  Когорты — по дате заявки/принятия в окне с исходами до конца дня наблюдения, а не календарные оплаты.
- На копии production 15.09: заявка → принят n = 24, p90 0,7 дн. → 1 день; принят → оплата n = 212, p90 20 дн.;
  заявка → оплата n < 20 → политика по умолчанию 14 дней (флаг).

## 5. Что статистика не делает

Не подгоняет α и пороги под результат, не суммирует дневных уникальных как уникальных периода, не считает эффект
между окнами с разным определением метрики, не использует LLM, не сравнивает календарные оплаты «до/после» как
конверсию, не объявляет причинность.
