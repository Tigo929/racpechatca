# ИИ-агент над CRM, сайтом и рекламой — архитектура

Написано 30.09.2026 по задаче: «есть сайт, есть CRM, есть два локальных MCP
(Директ и Метрика) — подключить ИИ-агента, чтобы была полнота картины».

## Короткий ответ

Агент живёт **на вашем сервере**, а не в облаке. Модель вызывается наружу
по API — и её можно менять. MCP-серверы остаются локальными и наружу
не смотрят.

```text
        Вы  ──►  Телеграм-бот  или  вкладка «Аналитика» в CRM
                          │
              ┌───────────▼────────────┐
              │   Агент-хост (Node)    │   контейнер рядом с backend,
              │   внутренняя сеть      │   наружу не опубликован
              └───┬────┬────┬──────┬───┘
                  │    │    │      │
      MCP Директ ─┘    │    │      └─ LLM API (deepseek-flash
      MCP Метрика ─────┘    │           или YandexGPT — переключается
      MCP CRM ──────────────┘           одной переменной)
      (его пока нет — см. ниже)
```

## Почему не Yandex AI Studio как хозяин агента

AI Studio это умеет: там есть MCP Hub и вызов функций, агент собирается
визуально. Но подключается он к MCP-серверу, **до которого дотянется
облако**. Ваши серверы локальные — значит, их пришлось бы выставить
в интернет: туннель, публичный адрес, своя авторизация. Это ключи от
рекламного кабинета и от статистики, выставленные наружу ради удобства
конструктора.

Держать агента у себя проще и безопаснее: наружу уходит только вызов
модели, а данные и токены не покидают сервер.

AI Studio при этом остаётся **вариантом модели**: YandexGPT вызывается
из вашего агента так же, как DeepSeek. Смысл идти в него целиком появится,
если понадобится голосовой агент или готовый конструктор без кода.

## Что проверено на вашем сервере

```text
api.deepseek.com          401   доступен, нужен только ключ
llm.api.cloud.yandex.net  404   доступен (YandexGPT)
api-metrika.yandex.net    404   доступен
api.direct.yandex.com     200   доступен — нужен только токен
api.telegram.org          000   НЕ доступен напрямую, работает через прокси
```

То есть обе модели с вашего сервера достижимы, а Телеграм — только через
тот же прокси, что уже настроен для бота и греетера. Это важно для
интерфейса: если делать телеграм-бота, он пойдёт через прокси.

## Чего не хватает: третьего MCP — по CRM

Директ и Метрика показывают, что было **до** заявки: клики, визиты, цели.
Деньги живут в CRM: заказы, оплаты, отказы, причины удаления, себестоимость.
Без третьего источника агент увидит «57 заявок по 247 ₽» и не сможет
сказать, что из них оплачено 8 и что реклама работает в минус.

Именно связка и есть та «полнота картины», ради которой всё затевается:

```text
клик → визит → заявка → заказ → оплата → выручка → прибыль
└── Директ ──┘└─ Метрика ─┘└──────── CRM ────────────────┘
```

Хорошая новость: считать заново ничего не надо. В CRM уже есть
`analytics/ads/ad-spend.ts` (CPL, CPA, CPO, ROAS, ROMI с честными
статусами «данных не хватает»), канонический P&L и происхождение заказов.
MCP по CRM — это тонкая обёртка над готовыми расчётами.

## Железное правило: модель не считает

Инструмент возвращает **готовые числа**, модель их только объясняет
и выбирает, какой инструмент позвать.

Соблазн отдать модели сырые строки и попросить «посчитай ДРР» велик —
и заканчивается уверенно неверной арифметикой, которую никто не проверит,
потому что выглядит она убедительно. Все формулы остаются в коде, где
на них есть тесты.

Из этого следует и практическое: инструменты отдают **агрегаты**, а не
выгрузки. Тысяча строк заказов в контексте — это и деньги за токены,
и потерянная точность.

## Инструменты, которые стоит дать агенту

Минимальный набор, закрывающий 90 % вопросов:

```text
MCP Директ
  campaigns_overview(период)         расход, клики, показы, CTR по кампаниям
  search_queries(период, кампания)   запросы: расход, клики, конверсии
  ad_groups(период)                  группы и объявления

MCP Метрика
  traffic(период)                    визиты, источники, устройства
  goals(период)                      достижения целей
  landing_pages(период)              страницы входа и конверсия

MCP CRM  ← сделать
  funnel(период)                     клик → заявка → заказ → оплата
  orders_summary(период, источник)   заказы, выручка, средний чек
  ad_economics(период)               CPL, CPA, ROAS, ДРР — из ad-spend.ts
  deletion_reasons(период)           почему удаляют заявки
  unit_economics(период)             P&L по каналам
```

Названия — глаголы от вопросов владельца, а не от таблиц. Модель выбирает
инструмент по описанию: «сколько стоит заявка» должно попадать
в `ad_economics`, а не заставлять её склеивать три вызова.

## Безопасность

```text
Токены            живут в MCP-серверах и .env. Модель их не видит никогда:
                  она получает результат вызова, а не ключ.
Персональные      телефоны, имена, ссылки на переписку в модель не уходят.
данные            Агрегаты обезличены по построению; где нужен пример
                  заказа — отдаём номер, а не контакт.
Запись            на первом этапе агент только читает. Менять ставки,
                  минус-слова и статусы заказов — отдельный этап и только
                  через «предложил → показал → вы подтвердили».
Доступ            агент-хост в внутренней сети docker, наружу не
                  опубликован. Интерфейс — телеграм-бот или вкладка в CRM
                  под существующей авторизацией.
```

## Выбор модели

С вашего сервера доступны обе. Разница:

```text
deepseek-flash    $0.30 за 1M входных, $1.20 за 1M выходных; вне пика
                  вдвое дешевле, попадание в кэш почти бесплатно.
                  Дёшево настолько, что стоимость можно не считать.
                  Данные уходят за пределы РФ — для обезличенных
                  агрегатов это приемлемо, для переписки с клиентами нет.

YandexGPT         дороже, но данные остаются в РФ, и это единственный
(AI Studio)       вариант, если однажды захочется давать модели тексты
                  переписки с клиентами.
```

Практический вывод: начать с `deepseek-flash`, а выбор модели спрятать
за один адаптер и одну переменную окружения. Переключение тогда стоит
строчки, а не переписывания агента.

Оценка расхода: один разбор «как дела с рекламой» — это 5–15 тысяч
токенов запроса и 1–2 тысячи ответа. Даже сто таких разборов в месяц
стоят меньше сотни рублей.

## Этапы

**Этап 1 — MCP по CRM, только чтение.**
Пять-шесть инструментов из списка выше поверх готовых расчётов. Проверяется
без всякой модели: вызвал инструмент — получил числа, сверил с отчётом.

**Этап 2 — агент-хост.**
Контейнер рядом с backend: клиент MCP к трём серверам, вызов модели,
системная подсказка с правилами (не считать самому, не выдумывать
источники, при нехватке данных говорить прямо).

**Этап 3 — интерфейс.**
Телеграм-бот (через существующий прокси) или вкладка в CRM. Бот удобнее:
вопросы задаются с телефона, ответы остаются в переписке.

**Этап 4 — регулярный разбор.**
Раз в неделю агент сам собирает сводку: что изменилось, где просело,
что предлагает сделать. Это уже почти готово — отчёты в `docs/analytics`
пишутся тем же набором данных.

**Этап 5 — действия, если захочется.**
Выключить фразу, поменять ставку, изменить бюджет. Только после того, как
чтение отработает месяц и станет понятно, чему агент не ошибается.

## Что стоит знать про надёжность MCP

В этой сессии ваш MCP Метрики отвалился с `CONNECTION_CLOSED` — просто
перестал отвечать. Для инструмента, которым пользуется человек, это
терпимо: перезапустил и работаешь. Для агента, который ходит по
расписанию, нет: он либо молча соврёт «данных нет», либо упадёт.

Поэтому MCP-серверы стоит завести как контейнеры с `restart: always`
рядом с остальными, а не запускать руками. И каждый инструмент должен
отличать «данных нет» от «источник недоступен» — это разные ответы,
и второй требует починки, а не выводов.
