# crm-mcp — CRM «Распечатка» как MCP-сервер

ИИ-агент спрашивает про бизнес обычными словами — «окупается ли реклама», «что
зависло», «сколько мы должны исполнителям» — и получает посчитанный ответ из
базы CRM. Двадцать семь инструментов покрывают все фундаменты системы: заказы,
деньги, реклама, каналы, производство, зарплата, маркетплейсы, качество данных.

## Три правила, на которых всё держится

**Только чтение, и это не обещание, а запрет базы.** Каждый запрос выполняется
внутри `BEGIN TRANSACTION READ ONLY` с таймаутом 15 секунд. Даже если однажды в
инструмент просочится `UPDATE`, Postgres его отклонит. Агент, «поправивший»
заказ, — то, чего здесь не должно случиться ни при какой ошибке.

**Считает код, а не модель.** Все доли, средние и цены уже посчитаны в ответе.
Деление на ноль даёт «—», а не `NaN` и не выдуманное число. Модели остаётся
объяснять, а не вычислять — там, где она вычисляет, она ошибается молча.

**Каждый инструмент говорит, чего он не знает.** Это часть описания, и это
проверяется тестом. Модель, не знающая границ инструмента, додумывает: увидев
ноль выручки у заказа с Ozon, она объявит, что продаж нет, — хотя деньги там
считает площадка.

## Чего сервер намеренно не делает

**Не считает прибыль.** Единственная верная формула себестоимости живёт в
`crm-new/src/reports/order-cogs.ts`; её же результат уходит в Метрику, и
равенство держат тесты. Повторить её в SQL значило бы завести вторую формулу
прибыли — она разойдётся с отчётом, и владелец получит два разных ответа на
один вопрос. Сервер отдаёт выручку и проведённые расходы, прибыль — в отчёте CRM.

**Выручку отдаёт так же, как отчёт, но только если попросить.** У P&L-отчёта
своё правило признания: заказ отдан клиенту ИЛИ оплачен, период режется по дате
признания (оплата, иначе завершение, иначе смена статуса, иначе отправка, иначе
создание), футболки с маркетплейса исключены. Это `revenue_summary` с
`basis=report` — единственный режим, который сходится с отчётом (сверено на
сентябре 2026: заказов 167, выручка 307 171 ₽, средний чек 1 839 ₽, по категориям
137 485 / 97 051 / 72 635 ₽). Режим по умолчанию `created` отвечает на другой
вопрос — «сколько наработали за период», — и в ответе об этом сказано прямо.

**Зарплата с отчётом не сойдётся, и это правильно.** Отчёт берёт её по заказам,
которые признал в периоде, а `salary_summary` — по дате начисления. Заказ,
признанный в сентябре, мог получить начисление в августе. Сводить эти числа
нельзя: это ответы на разные вопросы, и инструмент так и говорит.

**Не складывает посетителей Метрики по дням.** В Метрике `users` — уникальные
за день; сумма за неделю была бы больше настоящей. Отдаётся среднее за день,
а за уникальными за период — в интерфейс Метрики.

**Не приписывает заявки рекламе по догадке.** Рекламной считается заявка с
меткой клика Директа (`yclid`). Заявки с utm, но без метки, показаны отдельной
строкой и в цену заявки не входят: недосчитать — потерять точность, насчитать
лишние — потерять деньги на кампании, которая не работает.

## Инструменты

| Фундамент | Инструменты |
|---|---|
| Заказы | `orders_funnel`, `orders_by_status`, `orders_timeline`, `order_find` |
| Деньги | `revenue_summary`, `order_costs`, `prepayments` |
| Реклама | `ad_spend`, `ad_economics`, `ad_attribution` |
| Каналы | `channels_summary`, `site_traffic`, `site_landings` |
| Производство | `production_load`, `production_cycle`, `partner_dispatch`, `approvals_status`, `tasks_open` |
| Зарплата | `salary_summary`, `salary_debt` |
| Маркетплейсы | `marketplace_orders`, `marketplace_articles`, `stock_status` |
| Качество данных | `deletion_reasons`, `reviews`, `data_health`, `order_mix` |
| Прямой доступ | `schema_describe`, `sql_select` — запасной выход, только чтение |

Период задаётся `from`/`to` в формате `ГГГГ-ММ-ДД`; без них берутся последние
30 дней, потолок — 400 дней. Границы включительные: «с 1 по 28 сентября» — это
28 дней.

`data_health` стоит вызывать перед тем, как объяснять падение выручки или
конверсии причинами из жизни: частая причина — незаполненное поле, а не рынок.

## Свой запрос к базе, и почему записи нет

Двадцать семь инструментов отвечают на вопросы о деле. Если вопрос нестандартный
(«найди заказы с таким артикулом»), есть запасной выход: `schema_describe`
показывает устройство таблиц, `sql_select` выполняет один SELECT.

У него четыре ограничения, и каждое закрывает свою опасность:

- **Только чтение.** Запрос должен начинаться с SELECT или WITH; слова записи,
  вторая команда, комментарии, `SELECT … INTO` и функции вроде `pg_read_file`
  отклоняются с объяснением. Поверх этого — транзакция `READ ONLY`: даже в обход
  проверки Postgres отвечает `cannot execute UPDATE in a read-only transaction`.
- **Личные данные вырезаются** по именам колонок результата, поэтому `SELECT *`
  тоже обезличен: телефоны, ссылки на переписку, ключи, тексты сообщений
  заменяются на «скрыто». Переписка Авито и таблицы с ключами закрыты целиком.
- **Строк не больше 200**, ответ ограничен по длине: инструмент отвечает на
  вопрос, а не выгружает базу в контекст модели.
- **В каждом ответе сказано**, что числа в нём — арифметика модели, а не
  показатели CRM. Это не формальность: в CRM «выручка» — правило признания из
  P&L-отчёта, «оплачен» — заполненная дата, а не статус, «заявка с рекламы» —
  метка клика. Модель, пишущая SQL сама, выдумает свои определения, и ответ
  разойдётся с отчётом, оставшись убедительным.

**Записи через SQL не будет никогда — ни с подтверждением, ни «аккуратно».**
Дело не в страхе перед агентом, а в том, что в этой CRM запись — это не строка
в таблице. Один перевод заказа в «Оплачен» тянет за собой: пересчёт суммы,
запись в историю статусов (из неё аналитика выводит, когда заказ приняли в
работу), начисление зарплаты исполнителю и премии менеджеру, списание заготовок
со склада, расход на вознаграждение партнёру, строку в очередь к Метрике и
сообщение в Telegram. `UPDATE "OrderPhoto" SET status = 'PAID'` не сделает
ничего из этого — он оставит систему в состоянии, которого не бывает: заказ
оплачен, зарплата не начислена, склад не списан, в истории пусто, и аналитика
по нему считает неверно, не подавая признаков поломки.

Правильный путь для действий — узкие инструменты поверх API самой CRM
(«перевести заказ в статус», «отметить предоплату»), где всю эту логику
выполняет CRM, а агент только просит. Это этап 5 архитектуры, и по документу он
начинается после месяца работы на чтении, через «предложил → показал → вы
подтвердили».

## Запуск

Нужна одна переменная — строка подключения к базе CRM:

```
DATABASE_URL=postgresql://<пользователь>:<пароль>@<хост>:5432/<база>
```

Права пользователя лучше сузить до `SELECT` — read-only транзакция это уже
гарантирует, но два барьера надёжнее одного.

```bash
npm install
npm run build
npm start           # stdio: так подключаются агенты на этом же компьютере
PORT=3333 npm start # http://127.0.0.1:3333/mcp, если агент в другом контейнере
```

HTTP слушает только `127.0.0.1`, пока явно не задан `HOST`: в базе лежат заказы
и переписка, и открыть её в сеть по случайности нельзя.

### Подключение агента (stdio, локально)

```json
{
  "mcpServers": {
    "raspechatka-crm": {
      "command": "node",
      "args": ["C:/путь/до/racpechatca/crm-mcp/dist/index.js"],
      "env": { "DATABASE_URL": "postgresql://..." }
    }
  }
}
```

### Подключение к продакшн-базе (stdio через SSH)

Так это и развёрнуто. База CRM снаружи недоступна: у контейнера Postgres порт
открыт только внутри сети докера. Поэтому сервер живёт на сервере, рядом с
базой, а агент на ноутбуке запускает его разово через SSH — протокол идёт по
стандартному вводу уже существующего SSH-соединения, и ни одного нового порта
не открывается.

На сервере (однократно):

```bash
# исходники в /opt/raspechatka/crm-mcp
docker build -t crm-mcp:1.0.0 -t crm-mcp:latest .
# доступ к базе берётся из окружения бэкенда, наружу не печатается
umask 077
docker exec raspechatka-backend-1 sh -c 'printf "DATABASE_URL=%s
" "$DATABASE_URL"'   > /opt/raspechatka/crm-mcp/.env.mcp
chmod 600 /opt/raspechatka/crm-mcp/.env.mcp
```

В конфиге агента:

```json
{
  "mcpServers": {
    "raspechatka-crm": {
      "type": "stdio",
      "command": "ssh",
      "args": [
        "-T", "-o", "BatchMode=yes", "-o", "ConnectTimeout=20",
        "-o", "ServerAliveInterval=30",
        "-i", "C:/Users/<вы>/.ssh/id_rsa_gulian",
        "root@<сервер>",
        "docker run -i --rm --network raspechatka_internal --env-file /opt/raspechatka/crm-mcp/.env.mcp crm-mcp:1.0.0 node dist/index.js"
      ]
    }
  }
}
```

Контейнер живёт столько, сколько длится сессия агента, и удаляется сам
(`--rm`). Постоянно запущенного сервера нет — нечего забыть выключить.

Важно: в HTTP-режиме процесс не завершается при закрытии стандартного ввода,
поэтому `docker run` без `-e PORT=...` — не просто настройка, а условие того,
что контейнер уйдёт вместе с сессией. Ради этого PORT в образе по умолчанию
не задан.

После обновления кода образ надо пересобрать: агент запускает образ, а не
рабочую копию.

## Проверка

```bash
npm test        # период, формат, инварианты набора инструментов
npm run typecheck
node dist/smoke.js   # прогнать все инструменты по настоящей базе
```

`smoke.js` — обязательный шаг после правки любого SQL: типы TypeScript о SQL не
знают ничего, опечатка в имени колонки компилируется и падает только на живых
данных. Инструмент, падающий при первом вопросе владельца, хуже отсутствующего:
он выглядит работающим.
